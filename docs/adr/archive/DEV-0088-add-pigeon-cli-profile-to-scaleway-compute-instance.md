# DEV-0088: add a `pigeon-cli` cloud-init profile and an `ipv4_address` output to `scaleway/compute-instance`

- **Author**: Willow Finch ([@noisypigeon](https://github.com/noisypigeon)).
- **Date**: 2026-10-02.
- **Status**: Accepted.

## Context

ADR-0087 added a `profile` variable (`"rclone"` | `"docker"`) to `scaleway/compute-instance`, branching `local.cloud_init` between two provisioning shapes. The user wants a third profile, `"pigeon-cli"`, that provisions nothing via `packages:`/`write_files:` — its only job is to export a `BOOTSTRAP` environment variable holding:

```
curl -fsSL https://gist.githubusercontent.com/noisypigeon/1e96e8ef94380f913f6ae02782965149/raw/pigeon.sh | bash
```

so that after SSH'ing into an instance, the user can invoke it to bootstrap `pigeon-cli`.

**Invocation caveat, confirmed with the user.** Typing bare `$BOOTSTRAP` will not pipe correctly: bash/zsh only word-split an unquoted variable expansion — they don't re-parse the result for shell operators like `|`. So `$BOOTSTRAP` would invoke `curl` with the literal arguments `-fsSL`, `https://...`, `|`, `bash`, not a pipeline. The user wants to keep the literal `$BOOTSTRAP` env var as the interface anyway, and will invoke it as `eval $BOOTSTRAP` (which does re-parse the expanded string, running the pipeline correctly). This is called out here so it isn't a silent footgun for whoever next touches this profile.

Separately, the user asked for the instance's IPv4 address as a dedicated module output — today only `public_ips` (a list, mixing v4/v6 when both are enabled) and `private_ips` exist; there's no single-value way to get just the address a caller would actually connect to.

## Decision

### `profile` gains a third value, `"pigeon-cli"`

```hcl
variable "profile" {
  type        = string
  description = "Cloud-init provisioning profile: \"rclone\" (rclone/neovim + rclone.conf), \"docker\" (Docker CE), or \"pigeon-cli\" (exports a BOOTSTRAP env var; run as `eval $BOOTSTRAP`)"
  default     = "rclone"

  validation {
    condition     = contains(["rclone", "docker", "pigeon-cli"], var.profile)
    error_message = "profile must be \"rclone\", \"docker\", or \"pigeon-cli\"."
  }
}
```

`buckets`' existing guard validation (`var.profile == "rclone" || length(var.buckets) == 0`, ADR-0087) already correctly rejects `buckets` for `pigeon-cli` too — no change needed there.

### The `packages:` key becomes conditional

`pigeon-cli` needs zero packages. The existing template always emitted a `packages:` key (with `rclone`/`docker` conditionally contributing list items beneath it) — a `packages:` key with no items renders as `packages:` followed by nothing, which cloud-init/YAML treats as null rather than an empty list. Rather than risk that, the key itself is now wrapped in `%{if var.profile != "pigeon-cli"}...%{endif}`, so it's omitted entirely for `pigeon-cli` and unchanged for `rclone`/`docker` (verified by rendering all three profiles — `rclone`/`docker` output is byte-identical to pre-ADR-0088).

### `runcmd:` gains the `BOOTSTRAP` export, gated on `profile == "pigeon-cli"`

```hcl
    %{~if var.profile == "pigeon-cli"~}
      - echo "export BOOTSTRAP='curl -fsSL https://gist.githubusercontent.com/noisypigeon/1e96e8ef94380f913f6ae02782965149/raw/pigeon.sh | bash'" >> ~/.bashrc
    %{~endif~}
```

Follows the exact pattern `mise`'s activation line already uses in this same `runcmd:` block — appending to `~/.bashrc`, root-only (per ADR-0081, no sudo-user machinery in this module). `mise`'s install lines stay unconditional/common to all three profiles; nothing about `pigeon-cli` calls for removing it. `write_files:`/`rclone.conf` stays gated to `profile == "rclone"` only, unaffected by this change.

No change to `terraform_data.cloud_init`'s md5-hash + `replace_triggered_by` force-replace mechanism (ADR-0084) — it already covers any change to the rendered string regardless of which branch produced it.

### New output: `ipv4_address`

```hcl
output "ipv4_address" {
  description = "The instance's routed IPv4 address (null if enable_ipv4 = false)"
  value       = var.enable_ipv4 ? scaleway_instance_ip.ipv4[0].address : null
}
```

Sourced directly from the `scaleway_instance_ip.ipv4` resource `instance.tf` already creates when `enable_ipv4 = true` (ADR-0083/CHANGELOG 0.5.0) — more direct than filtering `public_ips` for the same value. Purely additive; `public_ips`/`private_ips` are unchanged.

### No manual `README.md`/`CHANGELOG.md` edits

Both are regenerated by `module-docs.yml`/`module-release.yml` on merge, same as every prior change to this module.

## Consequences

- `release:minor` — `profile` gains a new enum value (default unchanged), and `ipv4_address` is a new, additive output. No existing input/output changes.
- Any caller passing an unrecognized `profile` value already failed validation before this ADR; `"pigeon-cli"` is simply a third accepted value.
- Cloud-init content changes for every profile (the `packages:`-key restructuring touches the rendered string even for `rclone`/`docker`, though their final YAML is unchanged) → every existing instance using this module gets replaced on its next `terragrunt apply`, per the existing force-replace lifecycle (ADR-0084). This is true of any change to `local.cloud_init`, not specific to this ADR.
- `eval $BOOTSTRAP`, not bare `$BOOTSTRAP`, is required to actually run the bootstrap pipeline — documented here and in the module's `profile` description so it isn't rediscovered the hard way.

## Out of scope

- Hardcoding or templating the gist URL as a module variable — it's a fixed literal for this one profile; parameterize it if a second, different bootstrap script is ever needed.
- A shell function/alias wrapper that would let a bare `BOOTSTRAP` (no `$`, no `eval`) work — rejected; the user explicitly wants the `$BOOTSTRAP` env var interface and will use `eval`.
- An `ipv6_address` output mirroring `ipv4_address` — add if/when needed; not asked for here.
