# DEV-0141: pigeon.dev module documentation pages and a module-release post stream

- **Author**: Willow Graysen ([@noisypigeon](https://github.com/noisypigeon)).
- **Date**: 2026-10-07.
- **Status**: Accepted.

## Context

pigeon.dev (ADR-0130, ADR-0136) hosts only hidden, machine-facing redirect
pages today — one per `<provider>/<module>/vX.Y.Z` git tag, generated by
`workloads/pigeon.dev/generate-module-redirects.sh` (ADR-0109/0110/0114).
Each carries a `<meta name="terraform-get">` tag so `terraform init` can
resolve a short `pigeon.dev/modules/...` source URL; each is also
`in_search_index = false`, `include_in_feeds = false`, `hidden = true` — none
of them are meant to be browsed. There is no human-readable documentation
for any module anywhere on pigeon.dev, and release notes exist only
off-site, as GitHub Releases (`template-release.yml`'s tag/release step)
and in each module's own `CHANGELOG.md`.

This adds two visible things to pigeon.dev: a real page per module with a
usage example, and a post stream where every module release is a post whose
content is that release's changelog entry.

## Decision

### Generalize `changelog.html` (templates/zola-site)

`templates/zola-site/templates/changelog.html` listed its posts via a
hardcoded `get_section(path="changelog/_index.md")` instead of the `section`
variable Zola already passes into a section template — the only thing
stopping the template being reused by a second, differently-named section.
Fixed to use `section.pages` directly; behavior for noisypigeon.com's
existing `/changelog/` section is unchanged. This is a `templates/zola-site/`
change, so it rode ADR-0113's existing versioning track (`release:minor`,
cutting `templates/zola-site/v1.2.0`) — landed first, in its own PR (#232),
to keep its tag-cutting isolated from the pigeon.dev-only changes below.

### Module overview pages

`generate-module-redirects.sh` now also writes one **visible** page per
module (not per version) to `content/modules/<provider>-<module>.md`,
alongside the existing hidden per-version redirect pages (no naming
collision — those are `<provider>-<module>-vX.Y.Z.md`). For each module it
extracts, from that module's own `templates/terraform/<provider>/<module>/README.md`:

- a **description**: the paragraph between the `# <module>` heading and the
  next `##` heading (or the `<!-- BEGIN_TF_DOCS -->` marker, if the module
  has no other heading before it);
- a **usage example**: the contents of the fenced ` ```hcl ` block under a
  `## Usage` heading, verbatim, when one exists;
- the full sorted **version list** for that module, so the page can link to
  every version's existing (hidden) redirect page without the template
  needing to search for them.

Only 2 of the repo's 9 modules (`compute-instance`, `cockpit-observability`)
currently have a `## Usage` section in their README. Per an explicit
decision made while scoping this ADR, this is not backfilled as part of this
work: a module page without one just omits the usage example and links out
to the full README on GitHub — no synthesized fallback, and no rewriting of
whatever version is hardcoded inside an existing example (it reflects
whatever the module's own README says today, which may lag the module's
actual latest tag).

Two new **site-local** templates, under `workloads/pigeon.dev/src/templates/`
(not the shared theme — this "module catalog" concept has no other
consumer, matching how `module-redirect.html`/`theme-redirect.html` are
already pigeon.dev-local): `module.html` (the overview page itself) and
`modules.html` (a section-listing template for `content/modules/_index.md`,
grouped by provider, filtering on a new `extra.kind = "module"` discriminator
field so it only lists the new overview pages, not the existing hidden
per-version ones). `content/modules/_index.md` itself flips from
`render = false` / `in_search_index = false` to a real visible index.

### A `content/releases/` post stream

A new pigeon.dev section, `content/releases/`, holds one post per module
release. It needs no new template: `content/releases/_index.md` sets
`template = "changelog.html"` (now generic) and `page_template = "post.html"`
(already generic), the same two templates noisypigeon.com's own
`/changelog/` section uses.

### Wiring `template-release.yml` to write release posts

Inside the existing per-changed-module loop in `template-release.yml`'s
"Update changelogs and compute versions" step — which already computes the
next version and the PR's title/body/number/URL, and prepends an entry to
`${dir}/CHANGELOG.md` — a second write now lands alongside it:
`workloads/pigeon.dev/src/content/releases/<provider>-<module>-v<NEXT>.md`,
reshaping the same PR title/body/link into Zola front matter (version/date
become `title`/`date` instead of a `## [x] - date` / `### title` heading
pair). It's written and `git add`ed in the same step, so it's committed and
pushed in the same `chore: update changelog(s) for PR #N` commit as the
`CHANGELOG.md` update, and rides the existing post-tag pigeon.dev
`zola-sites-deploy.yml` dispatch (ADR-0136/0140) with no new trigger needed.

### Backfill

All 54 existing version-tagged entries across the 9 modules' `CHANGELOG.md`
files were backfilled into matching `content/releases/*.md` posts in one
content-only commit, using the same transform as the step above (parsing
each `## [X.Y.Z] - YYYY-MM-DD` / `### <title>` / body / `[#N](url)` entry).
This was an explicit scope decision: the release stream covers the repo's
full module-release history, not just releases going forward.

## Consequences

- pigeon.dev gains two new visible, browsable sections (`/modules/`,
  `/releases/`) with zero new shared-theme templates beyond the one-line
  `changelog.html` generalization.
- A module's documentation quality on pigeon.dev is now a direct function of
  its own README — adding a `## Usage` section to a module's README is both
  the existing terraform-docs-adjacent convention and, now, what makes that
  module's pigeon.dev page show a usage example.
- Every future module release (any PR merged through `template-release.yml`
  touching a `versions.tf`-containing module directory) automatically gets a
  pigeon.dev post with no further action from whoever lands that PR — same
  as the changelog entry and GitHub Release it already got.

## Out of scope

- Backfilling a `## Usage` section into the 7 modules that don't have one
  (`project`, `object-bucket`, `iam-policy`, `iam-application`,
  `iam-api-key`, `block-volume`, `grafana-dashboard`) — a deliberate,
  separate decision left to each module's own maintenance, not bundled into
  this ADR.
- Rewriting a module's hardcoded example version pin to match its current
  latest tag — the usage example is shown exactly as committed in the
  module's README.
- An RSS/Atom feed for `/releases/` — pigeon.dev has `generate_feeds = false`
  site-wide; adding feed support is a separate, future decision.
- Rendering inputs/outputs tables inline on a module's pigeon.dev page —
  that documentation stays on the module's GitHub README (linked from the
  page), not duplicated into Zola.
