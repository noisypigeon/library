# DEV-0097: move the pigeon-cli import/deduplication leaves to `workloads/pigeon-cli/terraform/`

- **Author**: Willow Finch ([@noisypigeon](https://github.com/noisypigeon)).
- **Date**: 2026-10-02.
- **Status**: Accepted.

## Context

Four Scaleway leaves under `terraform/infrastructure/scaleway/fr-par/` back jobs run by the external `pigeon` CLI (`noisypigeon/pigeon-cli`, split out of this repo by ADR-0084): three `import/*` object-storage buckets (`backblaze-import`, `macbook-scratch`, `email`, all under the `noisypigeon` namespace) and one `deduplication/macbook-scratch` leaf (compute instance + block volume + bucket, under the `pigeon` namespace). The latter's `compute.tf` passes `profile = "pigeon-cli"` to `modules/scaleway/compute-instance` — direct confirmation these are pigeon-cli's own job infrastructure, not just conventionally named. The user wanted all four relocated into the `workloads/<name>/terraform/` convention (ADR-0092, nesting depth widened by ADR-0096) as a new workload, `workloads/pigeon-cli/`, with explicit target paths:

- `scaleway/fr-par/noisypigeon/import/backblaze-import` → `workloads/pigeon-cli/terraform/import/backblaze` (renamed, dropping the redundant `-import` suffix now that it's nested under `import/`)
- `scaleway/fr-par/noisypigeon/import/macbook-scratch` → `workloads/pigeon-cli/terraform/import/macbook-scratch`
- `scaleway/fr-par/noisypigeon/import/email` → `workloads/pigeon-cli/terraform/import/email`
- `scaleway/fr-par/pigeon/deduplication/macbook-scratch` → `workloads/pigeon-cli/terraform/deduplication/macbook-scratch`

Pure relocation — no `.tf` resource content changes, no cloud resource created/destroyed. `workloads/pigeon-cli/` has no `src/` sibling, same as `workloads/scaleway/` (ADR-0094): it's infra backing an externally-repo'd tool's jobs, not a deployable app in this repo.

**Research confirmed, verbatim, before planning anything — this move needed less new wiring than either prior leaf-move this session (ADR-0094, ADR-0096):**

- Every local these four leaves' `.tf` files reference — `local.scaleway_project_id` (all three `iam.tf`s, and the deduplication leaf's block-volume), `local.ssh_key_public_key` (its compute instance) — was already generated by `workloads/root.hcl` (added by ADR-0094). No new provider wiring or generated locals needed.
- All four leaves are `fr-par`, matching `workloads/root.hcl`'s existing hardcoded `fr-par`/`fr-par-1` provider zone/region (ADR-0094's deliberate simplification, still valid — no `workloads/*/terraform` leaf needs a different region yet).
- `workloads/root.hcl`'s leaf-depth convention, widened by ADR-0096 to "any depth under `<name>/terraform/`," already admits these paths (e.g. `pigeon-cli/terraform/import/backblaze` is 4 segments, segment 1 is `terraform`) with no further change.
- A grep for `ENV_SW_`-prefixed locals (the `scaleway/root.hcl`-only `bucket_names_generated.tf` mechanism, deliberately not ported to `workloads/root.hcl` by ADR-0094) turned up a stray `ENV_SW_IMPORT_MACBOOK_SCRATCH_BUCKET_NAME` in `.env` — but it's unreferenced in any `.tf` file repo-wide, including the leaf it'd nominally name. Dead config, irrelevant here.
- A repo-wide grep for `dependency`/`dependencies` Terragrunt blocks found none referencing any of these four leaves' outputs (`access_key`/`secret_key`/`ip_address`) — safe to move without touching any other leaf.
- Scaleway credentials (`SCALEWAY_ACCESS_KEY`/`SCALEWAY_SECRET_KEY`/`SCALEWAY_ORGANIZATION_ID`) are global/unbranched in both `scaleway/root.hcl` and `workloads/root.hcl` — no per-namespace (`noisypigeon` vs `pigeon`) split exists anywhere for Scaleway, unlike the Cloudflare per-domain token-scoping gotcha ADR-0096 hit live. No credential surprises are expected here, but — per that same lesson — this should still be confirmed live via `terragrunt plan` during the state migration, not assumed.

## Decision

### Move, don't rebuild

```sh
git mv terraform/infrastructure/scaleway/fr-par/noisypigeon/import/backblaze-import workloads/pigeon-cli/terraform/import/backblaze
git mv terraform/infrastructure/scaleway/fr-par/noisypigeon/import/macbook-scratch   workloads/pigeon-cli/terraform/import/macbook-scratch
git mv terraform/infrastructure/scaleway/fr-par/noisypigeon/import/email             workloads/pigeon-cli/terraform/import/email
git mv terraform/infrastructure/scaleway/fr-par/pigeon/deduplication/macbook-scratch workloads/pigeon-cli/terraform/deduplication/macbook-scratch
```

All 13 tracked files move byte-for-byte. Each leaf's `terragrunt.hcl` is this repo's unchanged boilerplate (`include "root" { path = find_in_parent_folders("root.hcl") }`), which resolves correctly at the new depth exactly as the fastmail leaves did under ADR-0096.

**A real `git mv` gotcha hit live, worth recording**: pre-creating the destination's grandparent-and-parent directories in one `mkdir -p` (`workloads/pigeon-cli/terraform/import` and `.../deduplication`) and then running all four `git mv`s back-to-back in a single shell invocation produced a double-nested, wrong tree (e.g. `import/backblaze/backblaze-import/bucket.tf` instead of `import/backblaze/bucket.tf`) — despite the leaf-level destination (`import/backblaze`) not existing beforehand, which should have been a clean rename. The cause wasn't fully isolated, but re-running the same `git mv` commands **one at a time, verifying the resulting tree with `find` immediately after each**, produced the correct flat structure every time. No data was lost (`git reset` + `git checkout HEAD -- <path>` recovered the pre-move originals cleanly, since nothing had been committed yet) — but this is the reason to never batch directory `git mv`s blind when the destination nests more than one level deep; verify after each one.

### No `workloads/root.hcl` changes needed

Confirmed above: provider wiring, `scaleway_project_id`, `ssh_key_public_key`, the leaf-depth convention, and the remote-state key pattern (`workloads/${path_relative_to_include()}/terraform.tfstate`) were all already correct for these four new leaf paths.

### Consequences for the old tree

`terraform/infrastructure/scaleway/fr-par/noisypigeon/import/` loses all three children and disappears; `terraform/infrastructure/scaleway/fr-par/pigeon/` loses its only child (`deduplication/`) and disappears too (both removed via `rmdir` once empty — git doesn't track empty directories, so no `git rm` was needed). `terraform/infrastructure/scaleway/fr-par/noisypigeon/custodian/dhj/` and `terraform/infrastructure/scaleway/nl-ams/custodian/dj/` are untouched and keep `terraform/infrastructure/scaleway/root.hcl` very much alive — unlike the Cloudflare case (ADR-0096), there is no provider-root decommission here.

### Documentation

`workloads/README.md` gains a `pigeon-cli/` entry in its tree example (alongside `blog/`, `email/`, `scaleway/`), noting — like `scaleway/` — that it has no `src/` sibling. `docs/USAGE.md` and `CLAUDE.md` gain the corresponding bullets/mentions.

### The actual state migration — performed live, all four leaves verified clean

At the user's request (as with ADR-0096), the migration was executed directly in this session. Same runbook as ADR-0094/0096 — plain `terragrunt init`/`init -migrate-state` does not work across a directory move (Terragrunt's local init-pointer is keyed by filesystem path), so the move went through `terraform state pull`/`push` via a temporary worktree at HEAD (the move was still uncommitted when the migration ran, so `git worktree add <path> HEAD` was sufficient — no need to locate an earlier commit), once per leaf:

```bash
git worktree add <scratch>/old-pigeon-cli-leaf HEAD
cp .env <scratch>/old-pigeon-cli-leaf/.env   # gitignored, not checked out by worktree add

cd <scratch>/old-pigeon-cli-leaf/terraform/infrastructure/scaleway/fr-par/noisypigeon/import/backblaze-import
terragrunt init -input=false
terragrunt state pull > <scratch>/backblaze.tfstate   # 5 resources confirmed present

cd /Users/pigeon/Developer/noisypigeon/workloads/pigeon-cli/terraform/import/backblaze
terragrunt init -input=false
terragrunt state pull   # 0 resources, confirmed empty before pushing
terragrunt state push <scratch>/backblaze.tfstate
terragrunt plan -input=false   # "No changes. Your infrastructure matches the configuration."
```

Repeated identically for the other three leaves (resource counts pulled: `macbook-scratch` 2, `email` 5, `deduplication/macbook-scratch` 11 — the richest of the four, covering its compute instance, block volume, bucket, and IAM application/policy/key). Neither `state pull` nor `state push` calls the Scaleway API — only `plan`'s refresh step does, and that's the step that would have surfaced any credential/project-scope issue (none occurred, confirming the "Scaleway creds are unbranched" research finding above rather than just assuming it). All four leaves showed **"No changes."** after their push, confirming no resource was destroyed, recreated, or modified. Worktree and temp state files were removed afterward.

## Out of scope
